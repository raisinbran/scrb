# Agenda-to-notes N2 stage 1: scorer fixes, reconciliation, short local-model comparison

**2026-11-25 | Dev-only | Plan: [agenda-to-meeting-notes](../plans/agenda-to-meeting-notes-20261125.md) slice N2; follows [N1 pilot](agenda-notes-n1-pilot-20261125.md).** Invented data only. No owner recordings, agendas or notes were used. No IPC, UI, storage, contracts or Electron changes.

## Model and runtime (owner-approved download, kept outside the repo)

- Model: Qwen2.5-7B-Instruct, official `Qwen/Qwen2.5-7B-Instruct-GGUF`, Q4_K_M, two shards (3,993,201,344 and 689,872,288 bytes), Apache-2.0. SHA-256 matched the published values (`dfce12e3...80db`, `539cf93f...d72a`).
- Runtime: llama.cpp b12751 Windows Vulkan build (39 MB zip, SHA-256 matched the release digest). The owner approved a release zip of up to roughly 0.5 GB; this one is smaller.
- Hardware: Regiurn reports an RTX 3080 with 12 GB, not the 6 GB in the brief. With all layers on the GPU and a 12,288-token context, the server added about 4.9 GB of VRAM (7,380 MiB used against a 2,401 MiB baseline). On a real 6 GB card the weights (4.7 GB) plus cache would be tight; partial CPU offload (`-ngl`) would be needed. Not measured.

## Comparison (invented meetings, trigram stand-in embedder)

Setup. Three invented meetings per run (216 to 227 lines, 3,100 to 3,300 words, 2 chunks, 12 reference facts: 3 decisions, 2 dates), generated by `agenda-synth.ts`. Task A prompt versus agenda-aware prompt on identical transcripts, same scorer. Task A has no fact kinds, so it is scored kind-agnostic (generous) and strict. **Not used:** AMI (no fixtures on this machine, no download approved) and the MiniLM embedder (not installed); the trigram embedder is an offline stand-in whose tau was not retuned. Counts are per three meetings pooled.

| Task A, strict kinds  |             0/9 |         0/6 |          4/13 |           13/13 | 1.33, 1.17, 1.08            |                2/6 |

Diagnosis on seed 1 (invented text): v1's example output carried an `owner` field and the model filled it with the speaker's name on every fact, so verification rejected every fact as unsupported; it also returned only 4 to 6 facts per chunk. The prompt was changed (no owner in the example, kinds defined, "list every decision, date, caveat, action, question"; hash `5b4b21888ea03152`) and run once on fresh seeds 4-6, not the diagnosed ones.

Cost. Per-meeting wall time for both prompts together: 7 to 25 s (the first call included warm-up); agenda-aware 3.4 to 7.1 s per meeting, Task A 2.4 to 3.7 s (after warm-up). Whole runs: 41 s and 28 s. Peak llama-server working set 6.3 GiB (run 1) and 8.0 GiB (run 2); peak GPU use 7.3 GB and 7.0 GB total (about 4.9 GB above baseline). Model load about 21 s. Setup, runs, scoring and cleanup took about 3.3 minutes of the 20-minute budget (17:40 to 17:43 PST).

## What this does and does not show

- Agenda-aware v2 beat Task A on decision recall (5/9 against 0/9 strict) and returned parseable JSON on 12/12 chunks (Task A 9/12). That clears the "90% of chunks" gate from N1 for the agenda prompt only.
- It fails the plan's product bars by a wide margin: date recall 0/6, hallucination 38% (bar 5%), valid citations 82% (bar 100%). Date recall of 0 is probably kind mislabeling (the model files dates as `info` and strict matching refuses them); I did not re-score kind-agnostic for the agenda prompt, so that is a hypothesis.
- Seeds 1-3 were used to find the prompt problem, so run 1 is not a held-out number; run 2 is the first untuned run of v2 but only one run on three invented meetings with a generator that has simple templates.
- Cross-chunk reconciliation fired zero times on these meetings (no duplicates or reversals across chunks), so it is covered by unit tests only, not by model evidence.
- Nothing here predicts results on real meetings. The private held-out campaign is a later step that needs separate owner approval with a time estimate.
