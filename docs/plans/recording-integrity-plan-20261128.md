# Gate 8 recording integrity — diagnosis and proposed fix (2026-11-28)

**Proposal only.** Gate 8/V03 remain open. Base main 89c2a4c9. Independent review and explicit owner approval are required before risky capture changes or physical/long tests. No recording, code change or threshold change in this PR.

## Evidence and diagnosis

The [Nov 25 report](../gates/gate-8-drift-diagnosis-and-rerun-20261125.md) and merged [#496](https://github.com/raisinbran/scrb/pull/496) describe an isolated 72-minute helper run with a generated tone, muted speakers, 864 chunks per track, clean stop and no reported stalls. Corrected differential timeline drift was 10.68 ms (PASS against 50 ms), largely the single meeting gap. **Lost-audio FAIL is unchanged.** The older 65.81 ms drift was a chunk-length comparison artifact, not evidence of the cause of these failures. The source report gives aggregated results; original per-packet data and the local run folders are unavailable here. No private audio or transcripts were read.

| Observation | Leading explanation and support | What would falsify it |
| --- | --- | --- |
| **10.64 ms unmarked meeting gap at minute 19.1** | Plausible missing or skipped capture buffer: 512 frames at 48 kHz last 10.667 ms (the earlier run used this buffer size; confirm the actual rerun rate/size). A missing callback, empty/invalid buffer, ring overflow or device/tap discontinuity could produce this step. A single timestamp re-anchor with contiguous sample data is also plausible; frame counts and chunk timestamps alone cannot distinguish them. Clean stop and low CPU/no stalls make a prolonged overflow less likely, not impossible. | Inspect numeric logs around the boundary: previous and next callback host/sample times, flags, actual rates/frame counts, ring drops and chunk counts. Continuous sample indices and complete decoded synthetic marker sequence would refute a missing-buffer explanation; a sample-index discontinuity or proved missing accepted frames would refute a timestamp-only explanation. |
| **18.6 ms mic worst-hour net overlap** | Stronger explanation: common-mode sample-clock versus host-clock rate mismatch, not one 18.6 ms duplicated block. The report gives -22.49 ms mic and -11.82 ms meeting cumulative steps; excluding the +10.64 ms meeting gap gives -22.46 ms meeting, within 0.03 ms of mic. -22.49 ms over 4,320 s is about -5.2 ppm; at 48 kHz that is about one sample per 5-second chunk, consistent with the reported shared slope in both runs. | Fit separate slopes within stable-rate/device epochs; compare host elapsed time to continuous hardware sample counts and decoded sample totals. Abrupt steps, duplicate/missing sample indices, changing slopes not explained by device epochs, or lost/repeated synthetic markers would contradict the simple clock-rate explanation. A fitted slope alone does not prove continuity. |

The 18.6 ms failure is an absolute net of sub-2 ms differences in a clock hour, per [guards.mjs](../../scripts/long-run/guards.mjs), not a discrete overlap. The current 10 ms/hour and 100 ms/run limits are provisional; ~5.2 ppm would accumulate ~150 ms over eight hours. Do not reinterpret that as measured audio loss, or waive the guard before independent sample evidence. See the [lost-audio rule proposal](../handoffs/2026-11-14-lost-audio-rule-proposal.md) and [Regiurn calibration evidence](../handoffs/2026-11-14-regiurn-jitter-numbers.md).

## Pipeline finding (source, not proven root cause)

- [Capture.swift](../../native/macos-capture/src/Capture.swift): both IO callbacks hand host timestamps and buffers to rt_capture. [rt.h](../../native/macos-capture/src/rt.h) stores frame counts, nominal rate and host time, but not hardware sample time; empty/invalid buffers can return early, and full-ring drops increment a counter. [main.swift](../../native/macos-capture/src/main.swift) health emits framesDropped. The report does not establish whether any of these happened at minute 19.1.
- Track.drain in main.swift compares a packet's host time to nextHost (prior host plus frames/nominal rate). It splits a positive discontinuity only above **50 ms**. A 10.64 ms event can remain inside a chunk or be treated as ordinary rollover. The approved [capture clock plan](capture-contract-and-clock.md) calls for marking gaps above 2 ms. This is a demonstrated detection/reporting mismatch, not proof of dropped samples.
- [Chunks.swift](../../native/macos-capture/src/Chunks.swift) logs endNs from start plus nominal frames/rate. [recovery.ts](../../packages/app-core/src/recovery.ts) reconstructs duration from Opus granules and skips ordinary rollover gaps below 50 ms. [overnight.mjs](../../scripts/long-run/overnight.mjs) reads saved chunk logs and sealed facts; guards.mjs counts unmarked differences of at least 2 ms and checks frame evidence. Mac logs lack the missingCause/missingBeforeMs fields used for explicit helper-marked spans. The report's gap is consistent with this mismatch. Compare original log and sealed boundary values before attributing it to capture or encoding. A nominal frame-derived duration is not independent proof of packet continuity.

## Smallest conditional fix

1. **Read-only evidence first (1–2 hours):** from the retained Nov 25 run, extract only numeric metadata for the suspect boundary and nearby chunks (both tracks, raw log and sealed manifest, frame/rate/open/close reasons, helper events, drop counters); compare neighboring rollover steps and stable-rate slopes. No audio access, no rewriting historical reports, and no rerun if metadata is insufficient. Preserve the original evidence outside Git.
2. **If unresolved: bounded diagnostic slice (~150–300 LOC):** add numeric host/sample-time validity and sample-index/accepted/drop-count diagnostics to Capture.swift/rt.h and Track.drain, covering empty buffers, ring overflow, device/gate generations and writer input. Preallocate bounded storage; emit off the realtime thread, never block or allocate in callbacks. A short invented-input test must distinguish true missing frames, duplicates and a timestamp jump. No automatic default behavior change.
3. **If loss proved (~250–450 LOC):** correct the demonstrated drop path only; e.g. fix a proved buffer rejection or writer/ring issue, not a speculative buffer-size increase. Split and explicitly mark confirmed gaps at the existing 2 ms boundary, including a matching duration/cause in internal chunk metadata; ensure recovery and guards agree even at rollover. Do not add silence, discard samples, shift timestamps or label a 10.64 ms loss PASS merely by marking it (10 ms maximum marked gap; 100 ms total per run). Prove correct handling of pauses, rate changes, restart, stop and recovery. A timestamp-only jump must remain visible as uncertainty, not be misclassified as known lost sound.
4. **If continuous sample evidence proves common-mode rate mismatch:** propose a separate verifier-only calibration slice (~150–300 LOC). Report physical continuity, residual discontinuities and host/sample-rate slope separately; retain uncorrected figures and existing differential drift tests, including the 25 x 2.63 ms failing case. Do not simply detrend any stream or relax a limit to make this run pass: calibration must reject synthetic repeated loss/duplicates masquerading as slope. Any changed provisional acceptance rule needs explicit owner approval and independent review. Keep the original timeline and captured samples unchanged.
