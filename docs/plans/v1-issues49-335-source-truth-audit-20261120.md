## 2. Issue #49 — quit confirmation: existing lifecycle and focused plan

**Verified current source:**
- main/main.ts:275–280 has closed handlers but **no main-window close veto**; :379–381 calls app.quit when the last window closes on Windows. On macOS a window close leaves the app running, while application Quit/Cmd+Q enters quit events.
- main/main.ts:69–75 already destroys mini windows at before-quit. This happens **before** quit.ts:15–29 intercepts will-quit. A cancelled confirmation must not destroy mini state first.
- quit.ts:9–29 prevents default will-quit, starts backend.close once and calls app.exit(0) on completion, rejection, or the existing **15-second** limit. quit.test.ts:17–45 covers one close, rejection and timeout, **not** user cancellation.
- backend.ts:513–525 closes downloads/playback, stops summaries/titles/imports, starts finalPasses.shutdown, awaits recording.shutdown and then the final-pass shutdown/library.close. recording.ts:500–507 tries to stop/seal an active recording. FinalPassQueue.shutdown (app-core/final-pass.ts:309–316) aborts running/queued work; resumeFinalPasses (:451 onward) requeues interrupted final passes on a correctly configured next launch. **No checkpoint resume is promised.** A forced exit at the 15-second deadline is not proof that all audio was sealed; recovery preserves what was safely written where possible.

**Owner-approval-required implementation sequence (plan only):**

1. **Main-only state reader:** In main/backend.ts, expose on OpenedBackend a *main-process-only* criticalActivity() snapshot (recording.isBusy() and finalPasses.hasWork(), including queued work). Do not add Backend contract calls or renderer IPC. Read this synchronously when a quit is attempted; avoid basing a safety decision on possibly mixed renderer meeting statuses.
2. **Veto before side effects:** In main/main.ts, synchronously prevent the initiating **main-window close** and **app before-quit** when critical work exists. Use one reusable pending/approved/cancelled gate, preventing duplicate dialogs and reentrant quit attempts. The existing mini cleanup and any destructive shutdown must run **only after authorization**, not on an attempted quit that is cancelled. Do not warn for ordinary tab navigation, a mini-window hide or idle exit.
3. **Confirmation:** Use the existing native main-process dialog (no new IPC/security changes) with **Keep recording / Keep processing** as focused/default/cancel choice and **Quit and retry later** as the explicit destructive choice. Distinguish recording (stopping attempts clean finalization; interrupted saves may be recovered, not guaranteed complete) from queued/running final transcription (saved audio retained; pass will restart from the beginning later if the runner is available). Never promise percentage progress, checkpoint resume, or zero loss.
4. **Accepted intent:** Revalidate busy state on selection, set the approved-once token, then trigger the ordinary app.quit path. Preserve quit.ts's existing bounded backend.close and 15-second fallback pending specific safety evidence. Idempotently handle Windows last-window close, explicit menu quit, macOS Cmd+Q, repeated clicks, and a quit while a dialog is open. Cancellation returns to the intact window and leaves capture/final-pass workers running. Account for a recording that starts while confirmation is pending; no silent stale approval.
5. **Storage/recovery contract:** Do not mark a recording ready before its safe Stop/seal. Keep original chunks, manifests and any writer locks/recovery evidence; no deletion on quit. Interrupted final work keeps its persisted status and is retried later only when correctly configured. Explicitly distinguish normal process quit, time-bounded forced exit, crash and OS-forced shutdown; **the latter two cannot be guaranteed to show a dialog**.

**Proposed deterministic silent tests:** quit.test.ts (idle/no prompt, recording, queued/running final, default cancel, repeated trigger, confirmed quit once, failure and timeout); a focused main-window lifecycle test (Windows last-main-window close, macOS close versus Quit/Cmd+Q, mini-window retained after cancellation, no duplicate prompt or leaked event listeners); recording.test.ts (user-approved shutdown seals usable audio or leaves discoverable recovery evidence on failure); final-pass.test.ts (aborted work remains restartable from beginning, not checkpoint); a cancellation/race test for activity changing during an open prompt. No new real/audio/native tests under this assignment. **Separate owner approval** is required before lifecycle implementation, IPC/security changes, or device testing.
